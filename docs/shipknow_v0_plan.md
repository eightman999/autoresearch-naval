# shipknow v0: 艦艇理解 3 タスク pilot 計画

作成: 2026-10-06 / 状態: pilot 完了、結果は [shipknow_v0_pilot_report.md](shipknow_v0_pilot_report.md)。T3 単独学習による干渉診断はユーザー判断で省略

## 位置づけ

- 公開中の navspec v0.2（armament verdict）は維持し、触れない。R3 の追加学習は終了。
- 次フェーズの第一段階として、次の 3 タスクを Qwen3.5-0.8B の 1 モデル・マルチタスク SFT で成立するか確かめる。
  - T1 艦種判定
  - T2 武装・装備推測
  - T3 欠損諸元推測
- 艦艇設計（要求 → 設計 JSON → validator → 修正）は、この 3 タスクで艦艇知識が学べると確認できてから始める。
- MoE はタスク間干渉や容量不足を確認してから検討する。
- 0.8B でどこまで成立するかを確認した時点で止めて報告する。

## データ

- ソース: NSDB（Navypedia ミラー）の CLASS 11,144 行と SHIPS。実艦のみで、架空データは使わない。
- 1 艦級から複数のタスク例を作る。艦名・艦級名・来歴など、答えが漏れる文字列は入力から除く。
- train/valid/test は、艦級グループ単位（同名艦級・書き分け・譲渡艦をまとめる）で 80/10/10 に分ける。
- 出力は JSON のみ。
- T3 の数値は点推定で学習する。範囲と confidence は、推論時の複数サンプルから区間を作って評価する（学習ターゲットにはしない）。
- T1 の候補と confidence は、各艦種ラベルの条件付き尤度から出す。

## 評価

- 非 LLM ベースラインと同じ test で比べる。
  - T1: 多数派、kNN / 勾配ブースティング
  - T2: 近傍艦の武装
  - T3: (艦種×年代) の中央値、kNN 回帰
- 指標:
  - T1: accuracy、macro-F1、top-3、ECE
  - T2: 武装アイテム集合の F1、主砲口径、主砲門数、装備の有無、センサー種別
  - T3: 項目別 MAPE、±10% 以内率、区間被覆率
  - 共通: JSON 不正率

## 実行環境

- llm_master の RTX 3060（V100 は使わない）。
- 学習は `navspec_qwen35_verdict_train.py` と同じ方式（completion 位置だけで損失を取る）で、新しい汎用版を作る。

## 注意

- NSDB はミラー由来のデータ。学習済みモデルや派生データを外部公開する場合は、出典と利用条件を別途確認する。

## 今後の候補（2026-10-07 ユーザー提案、未着手）

### 艦歴・改装履歴を入れた時点つきの知識と対話
- 新 NSDB（2026-10-07 取り直し）の Project_history / Modernizations / Naval_service（改行区切り）、SHIPS の竣工・運命、`year` / `year_in_navy` を材料にする。
- 改装の記述を年表化する: (年, 変更, 装備)。まず規則で抽出し、取れない分だけローカル LLM で補う。艦級の武装を時点ごとの状態として持つ。
- 時点つきのタスクを作る: 「X 年時点の装備は？」「この改装は何年ごろ？」。設計フェーズの年代×装備の整合性チェックにも使う。
- 対話は検索で支える: 質問に応じて艦級レコードと年表を検索して入力に添える（v1 の近傍艦方式の延長）。0.8B に艦歴を暗記させない。
- 艦名を鍵として使うが、train/test は艦級単位で分ける方針を維持する。
- 来歴・艦歴は Navypedia の文章そのもの。文章の再現や公開モデルへの学習は利用条件を確認する。構造化した事実を中心にする。

### メモリ軽量化
- 学習時: 0.8B の bf16 重みは約 1.6GB で、ピーク 10.8GB の大半は入力長に比例する中間計算。勾配チェックポイント、近傍艦表示の短縮（入力の約 6 割）、損失計算の分割の順で効く。QLoRA は 0.8B では効果が小さい。
- 推論時: GGUF Q4/Q8 で 0.5〜0.8GB。

### 方針の確定（2026-10-07 ユーザー回答）
- メモリは**学習時の GPU メモリ**を優先する。勾配チェックポイントと近傍艦表示の短縮を先に入れる（艦歴を入力に添えると入力が長くなるため）。
- 艦歴・改装は**入力に添える**（出力として暗記させない）。
- 目標の使い方の例: 「1950 年ごろの、架空の戦勝国日本の巡視艇の設計」。
  - 学習は実在艦から作る。要求（国・年・艦種・任務・排水量の上限・速力・必要な装備）を元艦から逆算し、元艦に近い設計 JSON を答えさせる。入力に近傍の実在艦と艦歴・改装の年表を添える。
  - 推論では、架空の前提（戦勝国など）は要求文に書く。参考艦は検索で選ぶ（例: 1940 年代の日本の哨戒艇・駆潜艇、1950 年前後の米英の哨戒艇、戦後改装の年表）。
  - 出力は deterministic validator で検査し、違反を修正させる。validator の検査項目は、年代×装備、排水量、武装重量、寸法、出力×速力。
- 次の段取り（v1_2 の結果のあと）: (1) メモリ削減を学習スクリプトに入れる（計測は 3060 が空いてから）。(2) 設計タスクの試作データ（要求→設計 JSON、近傍艦と艦歴の年表つき）。

### MoE 風の構成（2026-10-07 ユーザー提案「モデルマージで」、未着手）
- 選択肢:
  - (1) タスク別 LoRA をタスクで切り替える（干渉ゼロ。llama.cpp で複数 LoRA を読み、リクエストごとに強さを変えられる）。
  - (2) タスク別 LoRA を TIES / DARE 等で 1 本にマージする（PEFT の `add_weighted_adapter`。Qwen3.5 での動作は未確認）。
  - (3) 学習ルータ（X-LoRA / MoLE 系）。
  - FFN を分割する本物の MoE への作り変えは、3060 では重いので対象外。
- 進め方の案:
  - タスク別 LoRA を同じ総 step 数で学習し、マルチタスク版と比べる（干渉診断を兼ねる）。
  - それを (2) でマージして、(1) とマルチタスク版の両方と比べる。
  - 設計タスクは T1〜T3 の LoRA を土台にして追加学習し、最後にマージする案もある。
- タスク別学習はデータが少ないので、3060 と V100（空いていれば）で並列に回せる。LoRA は r64 で 166MB、r16 なら約 40MB。
