## 4. 選定の根拠と既知の欠点

- **valid loss と生成指標が一致しない。** loss の最小は step 800 だが、生成した答えで測ると 1200 と 2000 の方が良い。status 一致・false_feasible・repair・context・E 認識がそうなっている。最終選定は生成指標で行った。
- **step 1200 を選んだ理由**
  - A〜D の正しく設計と E 認識を合わせた 5 カテゴリ平均が最高（72.4）。
  - 設計を返した行の要求充足が最高（89.4）。
  - design-v1 test の false_feasible が最低（17.4）。
  - context と ood が最良。
  - T1〜T3 の保持も s2000 より良い（T3 MAPE 17.0 対 18.4、ECE 2.5 対 4.6）。
- **既知の欠点: 根拠のない拒否**
  - 拒否の理由をもっともらしく作り、中身が事実と合わない。
    - 「1984 年に原子力推進は存在しない」（初出 1959 と自分で書いている）。
    - 「120mm 砲 8 門以上は不可、同規模の実艦は最大 12 門」（理由と結論が逆）。
    - 「1600t 以下の駆逐艦は最大 76mm 砲」（実際は 102mm 級がある）。
  - B（実艦で全充足できることを確認した問題）の 16%、C の 38%、D の 42% を拒否した。
  - 形式（conflicts / relaxations）は学習できたが、理由の数値は検証されていない。
- **トレードオフ**
  - 要求を全て満たした設計を返す率は、拒否を失敗と数えると v0（75.5）より低い（67.5）。
  - 不可能な要求の認識（0 → 92%）と、文脈・修正・連動の改善と引き換えになっている。

## 5. 次の対策案

1. **運用（すぐ使うなら）**: status が relaxed / infeasible のとき、conflicts の主張を決定論で照合する。たとえば同艦種・年代の実艦で満たせるかを train から引く。照合が通らない拒否は破棄し、「feasible で設計して」と再要求する。
2. **データ**
   - 「難しいが実艦で満たせる」要求に feasible の設計を返す例を増やし、過剰な拒否を抑える。C / D 型を中心にする。
   - 拒否の理由の数値は、入力に添えた参照値（近傍艦の最大値など）からだけ引かせる形式にし、モデルが数字を作らなくて済むようにする。
3. **学習**: best の選択を valid loss ではなく、小さな生成評価で行う（今回、loss と生成指標が逆向きだった）。
